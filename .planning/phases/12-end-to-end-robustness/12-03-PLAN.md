  <action>
Create an integration test file that proves the complete schema-change-to-sync pipeline works as a single integrated flow. The test imports actual codegen functions from the gateway module and actual validation schemas from the sync module, exercising the real code (not mocks) at every stage except the network call.

**IMPORTANT architectural note:** The pipeline has two separate schema systems:
1. Gateway-side: `generateZodSchema()` produces "database-structure" schemas in `shared/schemas/generated/*.generated.ts` (reflects PostgreSQL types/nullability only, no business rules)
2. Sync-side: `src/types/articulos.ts` etc. have Zod schemas with business validation rules (`.min()`, `.max()`, `.nonnegative()`, transforms)

The test must prove BOTH schema systems accept valid data, and that the codegen output format is structurally correct.

**Test structure (5 groups):**

**Group 1: Codegen produces correct Zod schemas from schema metadata (3-4 tests)**

Import `generateZodSchema` from `../../objetiva-sync-gateway/src/codegen/zod-generator.js` (cross-module import within monorepo).
Import `ColumnMetadata` type from `../../objetiva-sync-gateway/src/types/schema.js`.

Create a mock `SchemaResponse` for the "articulos" entity that mirrors the real PostgreSQL columns (use a subset: id, erp_codigo, erp_nombre2, nombre, precio, activo, plus standard auto-managed columns that get skipped). This represents the introspection output.

Tests:
- "generateZodSchema produces valid TypeScript with z.object for articulos": Call `generateZodSchema(mockSchemaResponse)`, assert the returned string contains `z.object({`, contains field names like `erp_codigo: z.string()`, `precio: z.number()`, `activo: z.boolean()`. Assert it does NOT contain auto-managed columns (id, creado, actualizado).
- "generated schema reflects nullable vs required correctly": Mock SchemaResponse with `erp_codigo` as NOT nullable and `nombre` as nullable. Assert output contains `erp_codigo: z.string()` (no .nullable) and `nombre: z.string().nullable().optional()`.
- "adding a new column to schema metadata produces updated Zod output": Create SchemaResponse with an extra column `{column_name: 'nueva_propiedad', data_type: 'text', is_nullable: true, default_value: null, ordinal_position: 99, column_comment: null}`. Assert the generated output contains `nueva_propiedad: z.string().nullable().optional()`.

**Group 2: Codegen produces correct Prisma schema from metadata (2-3 tests)**

Import `generatePrismaSchema`, `parseExistingSchema`, `mapToPrismaType` from `../../objetiva-sync-gateway/src/codegen/prisma-generator.js`.

Since `generatePrismaSchema` reads an existing schema.prisma file, use `mapToPrismaType` for unit-level verification of type mapping, and `parseExistingSchema` to verify the parser works on real content.

Tests:
- "mapToPrismaType maps PostgreSQL types to Prisma types correctly": Test integer->Int, bigint->BigInt (for id columns), text->String with @db.Text, decimal->Decimal with precision, boolean->Boolean, timestamptz->DateTime with @db.Timestamp(6).
- "parseExistingSchema extracts header and field maps from real schema": Read the actual `prisma/schema.prisma` file from the gateway module. Call `parseExistingSchema(content)`. Assert header contains `generator client` and `datasource db`. Assert fieldMaps is a Map (may be empty if no @map directives exist, which is fine).
- "a new column in ColumnMetadata would produce a new field in Prisma model output": Use `mapToPrismaType` with a new column `{column_name: 'nueva_propiedad', data_type: 'text', is_nullable: true, ...}` and assert it returns `{prismaType: 'String', dbAnnotation: '@db.Text'}`.

**Group 3: Generated schemas and sync schemas both accept valid fixture data (3-4 tests)**

This group proves the wiring: data created by test fixtures passes BOTH the sync-side Zod schema and the gateway-side generated Zod schema.

Import the gateway generated schemas: `ArticulosDbSchema` from `../../objetiva-sync-gateway/shared/schemas/generated/articulos.generated.js`.
Import the sync schemas: `articuloPayloadSchema` from `../../src/types/articulos.js`.
Import test data: `createArticulo`, `createComprobanteCabecera` from fixtures.

Tests:
- "articulo fixture validates against sync-side articuloPayloadSchema": Create articulo via `createArticulo()`, run `articuloPayloadSchema.safeParse(fixture)`, assert success.
- "articulo fixture validates against gateway-side ArticulosDbSchema": Create articulo, run `ArticulosDbSchema.safeParse(fixture)`, assert success. NOTE: The gateway schema is more permissive (no business rules) so if sync-side passes, gateway-side should too. But test both to prove wiring.
- "data shape from sync schema output is compatible with gateway schema input": Run `articuloPayloadSchema.parse(createArticulo())` to get the transformed output, then run `ArticulosDbSchema.safeParse(transformedData)` on it. Assert both succeed. This proves the sync->gateway data flow.
- "both schemas reject data missing required field erp_codigo": Create articulo without erp_codigo (override with undefined), assert both `articuloPayloadSchema.safeParse(...)` and `ArticulosDbSchema.safeParse(...)` fail.

**Group 4: Codegen output format consumed by gateway schema index (2 tests)**

Prove that the codegen output structure matches what `shared/schemas/index.ts` expects.

Tests:
- "generated Zod schema file exports named schema and type": Call `generateZodSchema()` with articulos SchemaResponse, assert the output string contains `export const ArticulosDbSchema = z.object(`, `export type ArticulosDbInput = z.infer<typeof ArticulosDbSchema>`.
- "all 4 entity generated schemas exist and export the expected names": For each of [articulos, comprobantes_cabecera, comprobantes_detalle, comprobantes_pagos], import the generated schema file and assert the named export (e.g., `ArticulosDbSchema`, `ComprobantesCabeceraDbSchema`) is a ZodObject (use `instanceof z.ZodObject` or check `_def.typeName`).

**Group 5: Complete pipeline flow - schema change to validated data send (2-3 tests)**

This is the critical end-to-end test. It simulates the entire workflow as a single flow.

Tests:
- "complete pipeline: schema metadata -> codegen -> validate -> send succeeds":
  1. Create mock SchemaResponse for articulos (simulating gateway introspection)
  2. Run `generateZodSchema(schemaResponse)` to get generated Zod file content (string)
  3. Verify the string is valid (contains expected fields)
  4. Create test fixture data using `createArticulo()`
  5. Validate against sync-side `articuloPayloadSchema` - assert success
  6. Validate against gateway-side `ArticulosDbSchema` (imported, not eval'd) - assert success
  7. Create mock API client via `createMockApiClient()`
  8. Send validated data via `mockClient.articulos.sendBatch([validatedData])` - assert success
  9. Assert sendBatch was called exactly once with the data
  This proves: introspection metadata -> codegen produces correct output -> fixture data passes validation -> API client accepts and sends.

- "pipeline with schema change (new column) maintains backward compatibility":
  1. Create SchemaResponse with a new nullable column `nueva_propiedad` (text, nullable)
  2. Run `generateZodSchema()` and verify new field appears in output
  3. Create fixture WITHOUT the new field (old data format)
  4. Validate against sync-side schema - should STILL pass (field is optional)
  5. Create fixture WITH the new field
  6. Validate against sync-side schema - should pass
  7. Send both through mock API client - both succeed
  This proves: schema evolution does not break existing data flow.

**Implementation notes:**
- Use cross-module imports via relative paths (monorepo, no package.json workspaces): `../../objetiva-sync-gateway/src/codegen/zod-generator.js`
- If cross-module import fails due to TypeScript paths, use `path.resolve()` + `readFileSync` to read the generated files directly and parse content with string assertions instead
- Mock the logger via `vi.mock('../../src/utils/logger.js')` to suppress output
- The `generatePrismaSchema` function reads `prisma/schema.prisma` from `process.cwd()`. For tests that call it directly, either mock `readFileSync` or use `mapToPrismaType` individually instead.
- Do NOT use `eval()` or `new Function()` to execute generated Zod code -- instead verify the string output structurally and use the already-imported gateway schemas for validation testing
