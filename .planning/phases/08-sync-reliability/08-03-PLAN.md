<objective>
Replace the gateway's record-by-record N+1 ingestion pattern with bulk operations using Prisma transactions, batch lookups, and createMany. This eliminates the performance bottleneck that makes each batch take 2-10 seconds instead of <1 second, compounding the timeout problem.

Purpose: The current IngestionService does individual `findFirst` + `create/update` for EACH record in a batch. For batch size 100, that's 200+ database queries per batch. For 1000 batches (100K records), this adds 2000-10000 seconds of gateway processing time. Bulk operations reduce this by 10-100x, making 100K+ record syncs practical within reasonable timeframes.

Output: Refactored IngestionService with bulk ingestion for all 4 entity types.
</objective>

  <action>
Refactor the `ingestArticulos` method to use a bulk pattern instead of record-by-record. The new approach:

**Step 1: Batch lookup of existing records**
Instead of `findFirst` per record, do ONE query to find all existing records:
```typescript
const erpCodigos = articulos.map(a => a.erp_codigo).filter(Boolean);
const existingRecords = await prisma.articulo.findMany({
  where: { erp_codigo: { in: erpCodigos } },
  select: { id: true, erp_codigo: true },
});
const existingMap = new Map(existingRecords.map(r => [r.erp_codigo, r.id]));
```

**Step 2: Separate into new vs existing records**
```typescript
const toCreate: typeof articulos = [];
const toUpdate: Array<{ id: number; data: typeof articulos[0] }> = [];

for (const articulo of articulos) {
  const existingId = existingMap.get(articulo.erp_codigo);
  if (existingId) {
    toUpdate.push({ id: existingId, data: articulo });
  } else {
    toCreate.push(articulo);
  }
}
```

**Step 3: Bulk create new records using createMany**
```typescript
if (toCreate.length > 0) {
  try {
    const createResult = await prisma.articulo.createMany({
      data: toCreate.map(a => ({
        ...a,
        erp_sincronizado: true,
        erp_fecha_sync: new Date(),
      })),
      skipDuplicates: true,
    });
    inserted = createResult.count;
  } catch (error) {
    // If createMany fails, fall back to individual creates
    for (const [index, articulo] of toCreate.entries()) {
      try {
        await prisma.articulo.create({
          data: {
            ...articulo,
            erp_sincronizado: true,
            erp_fecha_sync: new Date(),
          },
        });
        inserted++;
      } catch (createError) {
        errors.push({
          index,
          identifier: articulo.sku || articulo.codigo || `item-${index}`,
          error: createError instanceof Error ? createError.message : 'Error desconocido',
          code: 'INGESTION_ERROR',
        });
      }
    }
  }
}
```

**Step 4: Update existing records (still individual but within a transaction)**
Prisma does not support bulk update with different data per record. Use a transaction to batch the updates:
```typescript
if (toUpdate.length > 0) {
  await prisma.$transaction(
    toUpdate.map(({ id, data }) =>
      prisma.articulo.update({
        where: { id },
        data: {
          ...data,
          erp_sincronizado: true,
          erp_fecha_sync: new Date(),
          actualizado: new Date(),
        },
      })
    )
  );
  updated = toUpdate.length;
}
```

Wrap the update transaction in try/catch. If the transaction fails, fall back to individual updates and collect errors for each failed update.

**IMPORTANT CONSTRAINTS:**
- Preserve the existing `logIngestionResult` call at the end
- Preserve the existing `IngestionResult` return type
- Preserve the `metadata` parameter and its usage
- Remove all the per-record `logger.debug` calls (they spam logs with 100+ messages per batch)
- Keep one summary log for creates and one for updates instead
- The `performance.now()` timing must still wrap the entire operation

**DO NOT** change the method signature, return type, or the logIngestionResult call structure.
