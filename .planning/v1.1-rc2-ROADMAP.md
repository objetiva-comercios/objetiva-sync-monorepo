# Roadmap: v1.1-rc2 - Multi-Source & Hardening

## Overview

This milestone enables multi-origin synchronization by adding PostgreSQL as a data extraction source alongside SQL Server, implements origin tracking for audit trails, simplifies authentication workflows, adds production observability, and modernizes the gateway dashboard with shadcn/ui components. The work follows strict dependency ordering: adapter infrastructure first, then origin tracking, followed by independent auth and observability improvements, culminating in dashboard polish that visualizes all new capabilities.

## Phase Details

### Phase 1: PostgreSQL Adapter

**Goal**: Users can configure and execute sync queries against PostgreSQL databases using the same workflow as SQL Server.

**Depends on**: Nothing (foundation phase)

**Requirements**: MSS-01, MSS-02, MSS-03

**Success Criteria** (what must be TRUE):
1. User can create a PostgreSQL connection in the sync dashboard with host, port, database, and credentials
2. User can create a sync query that targets a PostgreSQL connection
3. User can execute a PostgreSQL sync query and see records flow to the gateway
4. Existing SQL Server connections and queries continue working unchanged

**Complexity**: MEDIUM | **Risk**: LOW

**Key Implementation Points**:
- PostgreSQLAdapter extends AbstractAdapter, implements IDataSourceAdapter
- Uses `pg` library (already present in gateway dependencies)
- Connection config stored in SQLite alongside SQL Server configs
- Dashboard connection form extended for PostgreSQL-specific fields

### Phase 2: Multi-Source Origin Tracking

**Goal**: Gateway tracks which data source wrote each record, enabling audit trails and last-write-wins conflict resolution.

**Depends on**: Phase 1 (adapter must exist before origin tracking)

**Requirements**: MSS-04, MSS-05, MSS-06, MSS-07, MSS-08, MSS-10

**Success Criteria** (what must be TRUE):
1. Every synced record has origin_source, origin_sync_id, and origin_synced_at populated
2. User can query gateway to see which source last modified a record
3. When two sources sync the same entity key, the later sync overwrites (last-write-wins)
4. Sync state tracks watermarks per source (not just per entity)
5. Conflict events (same record modified by two sources within 5 minutes) are logged

**Complexity**: MEDIUM | **Risk**: LOW

**Key Implementation Points**:
- Prisma schema migration adds origin columns to all entity tables
- Ingestion service extracts X-Origin-Source header from requests
- Sync module sends origin header with each batch
- sync_state table extended with sourceId column
- Conflict detection compares origin_synced_at within overlap window

**Plans**: 3 plans
Plans:
- [x] 14-01-PLAN.md - Origin Tracking Schema & Migration
- [x] 14-02-PLAN.md - Source ID Generation & Header Propagation
- [x] 14-03-PLAN.md - Conflict Detection & Integration Tests

### Phase 3: Auth Simplification

**Goal**: Users can set up and troubleshoot authentication without manual bcrypt hash generation or guessing at error causes.

**Depends on**: Nothing (independent of Phases 1-2)

**Requirements**: AS-01, AS-02, AS-03, AS-04, AS-05, AS-06, AS-07

**Success Criteria** (what must be TRUE):
1. Long-running syncs (>30 min) complete without token expiration errors
2. User can call /api/auth/diagnostics to see token validity, expiration, and configuration
3. Auth failure errors specify the exact cause (expired, invalid, missing, wrong secret)
4. First-time setup wizard generates secure credentials without manual CLI commands
5. User can change password through the dashboard
6. All auth changes maintain bcrypt + JWT + HTTPS security model

**Complexity**: MEDIUM | **Risk**: LOW

**Key Implementation Points**:
- Token refresh endpoint (/auth/refresh) issues new token before expiration
- AuthManager in sync module calls refresh proactively
- Diagnostics endpoint exposes non-sensitive token metadata
- Setup wizard generates bcrypt hash and JWT secret internally
- Password change requires current password verification

- [x] 15-02-PLAN.md - Auth diagnostics and password change endpoints

### Phase 4: Observability

**Goal**: Operations can monitor system health, debug issues with correlation IDs, and collect Prometheus metrics.

**Depends on**: Nothing (independent of Phases 1-3)

**Requirements**: OB-01, OB-02, OB-03, OB-04, OB-05, OB-06

**Success Criteria** (what must be TRUE):
1. Every log entry includes a correlation ID that tracks requests across sync and gateway
2. /health endpoint returns 200 with system status when healthy, 503 when degraded
3. /metrics endpoint returns Prometheus-compatible metrics (sync duration, record counts)
4. User can search logs by correlation ID to trace a sync operation end-to-end
5. Metrics show per-entity sync duration and record counts

**Complexity**: MEDIUM | **Risk**: LOW

**Key Implementation Points**:
- @fastify/otel for gateway instrumentation (replaces deprecated @opentelemetry/instrumentation-fastify)
- pino-opentelemetry-transport for log correlation
- Health endpoint checks database connectivity and critical services
- Prometheus exporter exposes sync_duration_seconds, sync_records_total histograms
- X-Correlation-ID header propagated from sync to gateway

## Phase Dependencies

```
Phase 1 (PostgreSQL Adapter) ----+
                                 +--> Phase 2 (Origin Tracking) --+
                                 |                                 |
Phase 3 (Auth) ------------------+                                 +--> Phase 5 (Dashboard)
                                 |                                 |
Phase 4 (Observability) ---------+-------------------------------+
```

**Dependency Rationale:**

1. **Phase 1 -> Phase 2**: Origin tracking requires an adapter to track origins from. The PostgreSQL adapter must exist before we can tag records with their source.

2. **Phases 1-4 -> Phase 5**: Dashboard modernization visualizes features from all prior phases:
   - Origin tracking columns (Phase 2) displayed in record views
   - Token status (Phase 3) shown in auth UI
   - Metrics (Phase 4) rendered in dashboard charts

3. **Phases 3, 4 Independent**: Auth and observability have no inter-dependencies. Could theoretically execute in parallel, but sequential execution preferred for focused context.

## Risk Assessment

| Phase | Complexity | Risk | Primary Risks | Mitigations |
|-------|------------|------|---------------|-------------|
| 1 | MEDIUM | LOW | Interface mismatch with IDataSourceAdapter | Review interface before implementing; pg library well-documented |
| 2 | MEDIUM | LOW | Clock skew between sources; migration for existing data | origin_synced_at timestamps; null handling for legacy rows |
| 3 | MEDIUM | LOW | Security regression while simplifying | Maintain bcrypt+JWT+HTTPS; security review before merge |
| 4 | MEDIUM | LOW | OpenTelemetry version churn | Pin versions; use official @fastify/otel |
| 5 | MEDIUM | MEDIUM | Breaking HTMX during React migration | Strict isolation; HTMX 100% test coverage before changes |

### Critical Pitfall Mitigations

From research findings:

1. **Per-query state breaks with multi-origin** (MSS-01)
   - Current: sync_state tracks lastSyncValue per query, not per source
   - Mitigation: Add sourceId column, track separate watermarks per source+entity

2. **Clock skew causes silent data loss** (MSS-02)
   - Last-write-wins assumes synchronized clocks
   - Mitigation: Add version counters, log conflicts when two sources touch same record within overlap window (5 minutes)

3. **Removing security while simplifying setup** (AS-01) - CRITICAL
   - Mitigation: Simplify UX only (wizard, messages, diagnostics). Maintain bcrypt, JWT validation, HTTPS.

4. **Breaking HTMX during partial migration** (DM-01)
   - Staged migration means HTMX and React coexist
   - Mitigation: Keep HTMX 100% functional until React replacement tested; use separate route prefixes

5. **Contract breaks between sync and gateway** (CC-04)
   - New headers/fields may break older clients
   - Mitigation: Version API (/api/v2/), add X-Sync-Version header for capability detection

## Phase Ordering Rationale

**User-specified priority order:** Multi-source -> Dashboard -> Auth -> Observability

**Research-recommended order:** 1 -> 2 -> 3 -> 4 -> 5

**Final order:** 1 -> 2 -> 3 -> 4 -> 5

**Rationale:**

1. **Phases 1-2 first**: Multi-source is the primary milestone goal. Database schema changes (Phase 2) must precede code that uses them. Adapter (Phase 1) must exist before origin tracking.

2. **Phase 3 before Phase 5**: User priority places Dashboard before Auth, but Dashboard needs Auth features (token status display, AS-05) to be complete. Building auth first enables dashboard to visualize it.

3. **Phase 4 before Phase 5**: Observability provides metrics that Dashboard visualizes (DM-05). Build metrics first, then display them.

4. **Phase 5 last**: Dashboard modernization is polish. All other features should work before adding UI improvements. This phase has highest risk (staged migration) and is safest to defer if timeline compresses.

## Constraints

Carried forward from PROJECT.md:

- **Physical Deployment**: Sync and gateway on separate servers - all multi-source features must work across HTTP
- **Tech Stack**: TypeScript, Fastify, Prisma, Zod, Drizzle - no framework changes allowed
- **Database**: PostgreSQL authoritative for gateway, SQLite for sync state - cannot change engines
- **Backwards Compatibility**: Existing sync configurations must continue working - no breaking changes
- **Security**: All auth changes must maintain or improve current bcrypt + JWT + HTTPS posture
- **Staged Migration**: HTMX dashboard must remain 100% functional until React replacement proven
